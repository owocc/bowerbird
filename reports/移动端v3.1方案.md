> 分支：`feature/mobile-v3`（含 v3 推送链路修复）
> 本轮只做方案，不写业务代码。开发轮按第 7 节逐文件清单执行。

## 0. 结论摘要

| 需求 | 结论 | 是否新增服务端接口 |
|---|---|---|
| 复制素材内容 | Android 原生 `ClipData` + `FileProvider`，Dart 先把原文件流式下载到 `cache/clipboard/`，再交给 Kotlin 放入剪贴板 | 否 |
| 复制信息文本 | 保留现有 `_copyCurrentInfo`，改名为「复制信息文本」并移入溢出菜单 | 否 |
| 视频播放 | `video_player`（官方，Android 走 ExoPlayer）。服务端 `originals` 已支持 Range，无需改服务端 | 否 |
| GIF 播放 | 详情页当前已使用原图而非缩略图；但 `photo_view 0.15.0` 的 `_ImageWrapper` 存在 `_imageInfo = _imageInfo` 自赋值缺陷，动图渲染不可靠。GIF 改走原生 `Image` 页面；网格对 ≤8MB 的 GIF 用原图并加 GIF 角标 | 否 |
| 删除素材 | `DELETE /api/v1/items/{id}`，内部调用既有 `MoveToTrash`，走废纸篓可恢复；广播已由 `MoveToTrash` 内的 `notifyItemsUpdated()` 覆盖 | **是** |
| 字段单独复制 | 详情弹层每个字段行尾加复制按钮，`Clipboard.setData` + SnackBar 反馈；标签/目录/调色板在分组标题处整组复制 | 否 |

## 1. 现状盘点

### 1.1 素材类型如何区分

`core/models.go` 的 `Item` 已包含判定所需全部字段：

```go
MimeType string  // image/gif、video/mp4 ...
Extension string // gif、mp4 ...
Meta     *ImageMeta // 其中 Animated bool（GIF/动图）
Size     int64
InTrash  bool
TrashedAt int64
```

`core/library.go` 已有权威判定函数：

- `IsImageExtension`：`png/jpg/jpeg/webp/gif/bmp/tiff/ico`
- `IsVideoExtension`：`mp4/mov/qt/webm/mkv/avi/m4v/flv/...`
- `DetectMimeType`：扩展名优先，gif → `image/gif`

移动端 `mobile/lib/models/item.dart` 的 `MobileItem` 已有 `isVideo`、`isAudio`，**缺少 `isGif`**；`MobileItemSummary` 没有 `isAnimated` 字段，也不需要新增：`extension == 'gif' || mimeType == 'image/gif'` 足够覆盖本期需求。视频判定沿用 `MobileItem.isVideo`，与网格角标现有逻辑一致。

结论：**不需要改数据结构**，只在 Dart 模型补 `isGif`（以及可选的 `isImage`）。

### 1.2 详情页现状

`mobile/lib/screens/detail_screen.dart`：

- 全屏 `PhotoViewGallery.builder`，每一页的 `imageProvider` 是
  `NetworkImage(ApiService.instance.getOriginalUrl(item.id))` —— **用的是原图，不是 `thumbnail.jpg`**。
- 顶部栏：返回、页码、下载、复制信息文本、分享、详情。
- 底部栏：文件名、尺寸/大小/日期、最多 4 个标签，点击打开元数据弹层。
- 元数据弹层 `_showFullMetadataSheet`：标题、拍摄/导入时间、尺寸、大小、MIME、主色、调色板、备注、来源 URL、Prompt、颜色模型/色彩空间/百万像素/相机、目录、标签。
- 复制只有 `_copyCurrentInfo`：拼接多行文本写系统剪贴板。
- 没有删除入口，也没有视频播放能力；`PhotoViewGallery` 对视频/音频只会显示破图。

### 1.3 网格现状

`mobile/lib/screens/home_screen.dart` 与 `search_screen.dart` 都是三列方形网格，统一使用
`Image.network(getThumbnailUrl(id))`，即服务端生成的 **静态 `thumbnail.jpg`**。
`home_screen.dart` 已对 `item.isVideo` 画右上角播放角标（第 669 行附近），`search_screen.dart` 也有类似角标。GIF 无角标，且网格中的 GIF 必然是静态首帧。

### 1.4 现有 API 端点

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/api/v1/status` | 否 | 服务状态 |
| POST | `/api/v1/pair` | 否 | 配对换 token |
| GET | `/api/v1/ws`（别名 `/ws`） | Bearer/query token | WebSocket |
| GET | `/api/v1/libraries` | 是 | 资源库列表 |
| POST | `/api/v1/libraries/switch` | 是 | 切换资源库 |
| POST | `/api/v1/upload` | 是 | multipart 上传 |
| GET | `/api/v1/items` | 是 | 分页/搜索/标签/目录/颜色/类型/方向过滤 |
| GET | `/api/v1/items/{id}` | 是 | 完整 Item |
| GET/HEAD | `/api/v1/thumbs/{id}` | 是 | 缩略图，缺失时回退原图 |
| GET/HEAD | `/api/v1/originals/{id}` | 是 | 原文件流 |
| GET | `/api/v1/tags` / `folders` / `colors` | 是 | 分类数据 |

**没有删除端点**。`HandleFunc("/api/v1/items/", ...)` 目前只接受 GET，DELETE 会落到 405。

### 1.5 Range 核查结论

`handleOriginal` 使用 `http.ServeFile`。Go 标准库中 `ServeFile → serveFile → ServeContent`，会自动处理 `Range`、`If-Range`、`HEAD` 并返回 `206 Partial Content` / `Accept-Ranges: bytes` / `Content-Range`。

已在本机用最小 Go 程序验证：`Range: bytes=2-5` 返回 `206`、`Accept-Ranges: bytes`、`Content-Range: bytes 2-5/20`、正文 `2345`。`core/mobile_api_test.go` 第 12 步也已断言 Range 请求返回 206/200 且带 `Content-Range`。

**服务端 originals 无需补 Range 改动。** 唯一注意点：`handleOriginal` 手动设置的 `Content-Type` 会被 `ServeContent` 保留，不会被覆盖。

### 1.6 删除现状

- `LibraryManager.MoveToTrash(id)` 已实现：写 `in_trash/trashed_at/trashed_folders`，删除 `item_folders` 关联，异步更新 `metadata.json`，调用 `mutateCachedItem`，最后 `notifyItemsUpdated()`（v3 推送修复已补齐）。
- `MoveToTrash` 对不存在的 ID **不报错**（`UPDATE` 0 行也返回 nil），因此 HTTP 层必须先查 `GetItem`。
- 对已在废纸篓的素材再次调用 `MoveToTrash` 会把 `trashed_folders` 覆盖成 `[]`（此时 `item_folders` 已为空），**会丢失恢复时的原始目录**。必须在 HTTP 层拒绝二次删除，并在 `MoveToTrash` 内加幂等保护。
- `GetItem` 的缓存 `itemsByID` 包含废纸篓素材，`InTrash` 可直接判断。

## 2. 剪贴板方案选型

### 2.1 Android 把文件放进剪贴板的标准做法

```kotlin
val uri = FileProvider.getUriForFile(context, "$packageName.fileprovider", file)
val clip = ClipData(
    ClipDescription(displayName, arrayOf(mimeType)),
    ClipData.Item(uri)
)
(context.getSystemService(Context.CLIPBOARD_SERVICE) as ClipboardManager)
    .setPrimaryClip(clip)
```

关键点：

1. 剪贴板里放的是 `content://` URI，不是字节；目标 App 粘贴时通过 `ContentResolver` 读取。
2. Provider 必须 `exported=false` + `grantUriPermissions=true`。剪贴板服务在粘贴方读取 URI 时会授予临时读权限（Android 标准行为）；FileProvider 本身也要求 `FLAG_GRANT_READ_URI_PERMISSION` 语义，`ClipData` URI 由系统处理。若个别 OEM 仍失败，保留「分享」兜底。
3. `ClipDescription` 显式带 MIME（`image/gif`、`image/jpeg`、`video/mp4`），避免部分 OEM 按 URI 猜错类型。
4. 剪贴板不复制文件所有权：源文件在 App 缓存中必须保留一段时间，不能 `setPrimaryClip` 后立即删除。

### 2.2 两种实现对比

| 方案 | 微信图片粘贴 | 视频/大文件 | 实现成本 | 风险 | 结论 |
|---|---|---|---|---|---|
| **FileProvider + 本地缓存文件** | 支持（`image/*` URI） | 需先落盘，500MB 级文件耗时/占空间 | 低：Dart 下载 + Kotlin 10 行 | 缓存清理、重复下载 | **采用** |
| 自定义 ContentProvider 直接流式代理 HTTP | 支持，但粘贴方可能在主线程同步读流，弱网卡顿/失败 | 不落盘，但需处理 Range、鉴权、并发、断线 | 高：Provider + HTTP 客户端 + token + 生命周期 | 粘贴目标 App 兼容性不可控；剪贴板预览可能读大文件 | 不采用 |
| 只放文本/路径 | 微信会粘贴成文字，不是图片 | 不适用 | 最低 | 不满足需求 | 不采用 |

选择 FileProvider 的理由：微信/QQ/备忘录/邮件对本地 `content://` URI 的兼容性最好；粘贴时无网络依赖；实现只需标准 API，不引入第三方插件。

### 2.3 微信兼容性边界（必须写进验收说明）

- 图片：微信聊天输入框长按 → 粘贴，可作为图片发送。
- GIF：作为 `image/gif` 粘贴，微信可能按图片发送；部分版本只保留首帧。**能粘贴，但不保证对方收到动图**。应用内详情页仍正常播放。
- 视频：微信聊天输入框不支持把视频 URI 直接粘贴成视频消息。视频请走现有「分享」或「下载」。剪贴板中的 `video/*` URI 可在文件管理器、Telegram、邮件等支持文件粘贴的 App 使用。
- 若某 OEM 的剪贴板服务不授予 URI 读权限（极少数），错误表现为目标 App 提示「无法读取」。此时保留「分享」作为兜底，不在本期做自定义 Provider。

### 2.4 缓存策略

- 目录：`getTemporaryDirectory()/clipboard/`（Android 上是 `cacheDir/clipboard/`，Kotlin 用 canonical path 校验必须位于该目录下）。
- 文件名：Dart 侧清洗 `item.filename`，只保留 `[A-Za-z0-9._-]`，无扩展名时补 `.<extension>`；重名加短哈希前缀，避免覆盖。
- 清理：每次复制前删除该目录下修改时间超过 24h 的文件；保留当前文件。
- 大小上限：500 MB（与上传上限一致）。超过时提示「文件过大，请使用分享或下载」，不开始下载。
- 下载：流式写文件，不把整个视频读进内存；`Content-Length` 缺失时用 `item.size` 估算进度。

## 3. 视频播放选型

### 3.1 方案对比

| 维度 | `video_player`（官方） | `media_kit`（libmpv） |
|---|---|---|
| Android 实现 | Media3 ExoPlayer | libmpv + FFmpeg |
| 自定义 header | 支持 `httpHeaders` | 支持 |
| Range/seek | ExoPlayer 原生支持 HTTP Range | 支持 |
| 格式 | mp4/webm/mkv/ts 等常见容器较好；avi/wmv/rmvb 等依赖容器与编码，可能失败 | 格式覆盖最全 |
| APK 体积 | +约 2–4 MB（Media3） | +20 MB 以上（多 ABI 更大） |
| 维护/接入 | 官方插件，接入成本低 | 需要初始化 `MediaKit.ensureInitialized()`，平台配置更多 |
| 结论 | **采用** | 本期不采用；若后续出现大量 avi/rmvb 再评估 |

### 3.2 播放器接入

`video_player: ^2.11.1`（本机 pub cache 已有，Flutter 3.47 可解析）。

```dart
VideoPlayerController.networkUrl(
  Uri.parse(ApiService.instance.getOriginalUrl(item.id)),
  httpHeaders: ApiService.instance.mediaHeaders, // 只带 Authorization/Accept
)
```

- URL 已由 `getOriginalUrl` 自动附加 `?token=`，同时再带 `Authorization`，双保险。
- 不自动播放：`initialize()` 后显示首帧，用户点播放。
- `setLooping(false)`；页面切换/离开时 `pause()`，`dispose()` 释放。
- 进度条用 `VideoProgressIndicator(allowScrubbing: true)`，时间文本用 `position`/`duration` 流或 `addListener` 刷新。
- 错误态：`controller.value.hasError` 或 `initialize()` 抛错时显示「该视频格式暂不支持播放」+ 文件名 + 「分享/下载」提示；不崩溃、不黑屏。
- 宽高比：`controller.value.aspectRatio`；`AspectRatio` + `BoxFit.contain`。
- 视频页面不套 `PhotoView`，避免 PhotoView 把视频当图片解码。

### 3.3 服务端是否需要改

不需要。`originals` 已支持 Range（见 1.5），`Content-Type` 由 `item.MimeType` 或 `DetectMimeType` 给出；Android 明文 HTTP 已在 manifest 开启 `usesCleartextTraffic`。

## 4. GIF 方案

### 4.1 现状与「为什么不动」

- 详情页：`PhotoViewGalleryPageOptions` 的 `imageProvider` 是 `getOriginalUrl`，**不是缩略图**；理论上 Flutter 的 `Image` 支持 GIF 多帧解码。
- 但 `photo_view 0.15.0` 的 `_ImageWrapperState.handleImageFrame` 里有一行 `_imageInfo = _imageInfo;`（自赋值，明显缺陷），且首帧后只更新尺寸/加载态，不再可靠地驱动后续帧。不同 Flutter 引擎/机型上表现为只显示静止首帧。该包已基本停更，不应把动图播放托付给它。
- 网格：`thumbnail.jpg` 是服务端生成的静态 JPEG，GIF 在网格必然是静止首帧。

### 4.2 改法

**详情页**：新增 `_AnimatedImagePage`，GIF（以及后续可扩展的 animated WebP）不走 `PhotoView`，改用原生 `Image`：

```dart
InteractiveViewer(
  minScale: 0.8,
  maxScale: 4.0,
  child: Center(
    child: Image.network(
      ApiService.instance.getOriginalUrl(item.id),
      headers: ApiService.instance.mediaHeaders,
      fit: BoxFit.contain,
      gaplessPlayback: true,
      loadingBuilder: ...,
      errorBuilder: ...,
    ),
  ),
)
```

- 原生 `Image` 的 `MultiFrameImageStreamCompleter` 负责逐帧刷新，`gaplessPlayback` 避免页码切换闪白。
- 静态图片继续用 `PhotoView`，保留双击/双指缩放。
- 视频页用播放器；三者统一放进 `PageView.builder`。

**网格（低成本部分）**：

- 所有 GIF 卡片增加左上角 `GIF` 角标（与右上角视频角标区分）。
- 仅当 `item.isGif && item.size <= 8MB` 时，用 `Image.network(getOriginalUrl(...), cacheWidth: 400)` 替代缩略图，让网格真正动起来；超过 8MB 或加载失败回退静态缩略图，避免一次拉取几十 MB。
- 8MB 阈值是折中：网格一屏最多 9 个可见 GIF，最坏 72MB 流量，仍可接受；大 GIF 保持静态 + 角标。

> 可选增强（不在本期必做）：服务端为 GIF 生成动图缩略图（WebP/缩小 GIF），需要改导入流水线，成本高，先不做。

## 5. 删除接口设计

### 5.1 接口

```http
DELETE /api/v1/items/{id}
Authorization: Bearer <token>
```

- `{id}`：`Item.ID` 或 `Item.Hex` 均可（沿用 `GetItem` 的 id/hex 查找）。
- 语义：移入废纸篓（`MoveToTrash`），**不是永久删除**。桌面端废纸篓可恢复。
- 鉴权：复用 `authMiddleware`（Bearer 或 `?token=`）。
- 路由：不新增 `HandleFunc`；在 `handleItemDetail` 内按方法分发。`/api/v1/items/` 前缀已注册，CORS 已允许 `DELETE`。

成功响应（200）：

```json
{
  "status": "success",
  "code": "OK",
  "data": { "id": "A1B2...", "inTrash": true }
}
```

失败响应沿用 `APIResponse` 信封：

| HTTP | code | 场景 | 移动端提示 |
|---|---|---|---|
| 400 | `INVALID_ID` | id 为空 | 参数错误 |
| 401 | `UNAUTHORIZED` | token 无效 | 请重新配对 |
| 404 | `NOT_FOUND` | id 不存在 | 素材不存在或已被删除 |
| 409 | `ERR_ITEM_ALREADY_TRASHED` | 已在废纸篓 | 该素材已在废纸篓 |
| 503 | `ERR_NO_ACTIVE_LIBRARY` | 桌面端未打开库 | 桌面端未打开资源库 |
| 500 | `ERR_DELETE_ITEM_FAILED` | `MoveToTrash` 失败 | 删除失败，请重试 |

实现顺序（`handleItemDelete`）：

1. `s.manager == nil` → 503。
2. `item, err := s.manager.GetItem(itemID)`；`err != nil || item == nil` → 404。
3. `item.InTrash` → 409（**必须在调用 MoveToTrash 前拦截**，防止覆盖 `trashed_folders`）。
4. `s.manager.MoveToTrash(item.ID)`（用 canonical `item.ID`，不要用 hex；`MoveToTrash` 更新 `metadata.json` 时按 `items/<id>` 找路径）。
5. `writeSuccess(w, map[string]any{"id": item.ID, "inTrash": true})`。

广播：`MoveToTrash` 内部已调用 `notifyItemsUpdated()`，HTTP 层不要重复广播。

### 5.2 幂等保护（`core/library.go`）

在 `MoveToTrash` 开头加：

```go
if existing, err := m.GetItem(id); err == nil && existing != nil && existing.InTrash {
    return nil
}
```

原因：移动端连点、双端并发删除时，第二次调用会把 `trashed_folders` 覆盖为空，导致桌面端恢复后丢失原目录。该保护不改变正常路径语义。

### 5.3 移动端交互

- 详情页顶部溢出菜单新增「删除素材」（红色文字）。
- 点击弹 `AlertDialog`：
  - 标题：删除素材
  - 内容：将移入桌面端废纸篓，可在桌面端废纸篓中找回。
  - 按钮：取消 / 删除（红色）
- 确认后按钮进入 loading，禁止重复点击；成功 `Navigator.pop(context, true)`。
- 列表页 `_openDetail` `await` 返回值；`true` 时：`_loadItems(refresh: true)`（首页）/重新搜索（搜索页），并 SnackBar「已移入废纸篓」。
- 服务端 `items_updated` 也会触发列表刷新；`_loadItems` 已有 `_pendingRefresh` 合并，不会重复请求。
- 失败：详情页 SnackBar 显示服务端错误，不返回。

### 5.4 为什么不做 `DELETE /api/v1/items/{id}?permanent=true`

移动端不提供永久删除，避免误操作不可恢复；桌面端已有 `PermanentDeleteItem`/清空废纸篓入口，保持单一职责。

## 6. 字段单独复制设计

在 `_showFullMetadataSheet` 内，把 `_buildMetaRow` 扩展为带行尾复制按钮：

```dart
Widget _buildMetaRow(IconData icon, String label, String value) {
  return Row(
    children: [
      Icon(icon),
      Text('$label: '),
      Expanded(child: Text(value)),
      IconButton(
        icon: const Icon(Icons.copy_rounded, size: 18),
        tooltip: '复制$label',
        onPressed: () => _copyField(label, value),
      ),
    ],
  );
}

Future<void> _copyField(String label, String value) async {
  await Clipboard.setData(ClipboardData(text: value));
  if (!mounted) return;
  ScaffoldMessenger.of(context).showSnackBar(
    SnackBar(content: Text('已复制$label'), duration: const Duration(seconds: 1)),
  );
}
```

逐字段取值（全部来自现有展示字段）：

| 字段 | 复制值 |
|---|---|
| 名称 | `item.name.isNotEmpty ? item.name : item.filename` |
| 文件名 | `item.filename` |
| 拍摄/导入时间 | `DateFormat('yyyy-MM-dd HH:mm:ss').format(item.dateTime)` |
| 尺寸 | `'${item.width} × ${item.height}'` |
| 大小 | `item.formattedSize` |
| 格式 | `item.extension.toUpperCase()` |
| MIME | `item.mimeType` |
| 文件路径 | `ItemDetail.filePath`（新增解析；为空则不显示该行） |
| 来源 URL | `detail.url` |
| 备注 | `detail.note` |
| Prompt | `detail.prompt` |
| 主色 | `detail.dominantColor.toUpperCase()` |
| 调色板 | `detail.palette.join(', ')`（分组标题右侧复制整组） |
| 颜色模型/色彩空间/百万像素/相机 | `detail.meta[...]` 对应值 |
| 标签 | `item.tags.join(', ')`（分组标题右侧复制整组） |
| 目录 | `item.folders.join(', ')`（分组标题右侧复制整组；当前展示的是目录 ID） |
| 尺寸文本 | 与详情弹层展示一致，不额外加单位后缀 |

- 复制按钮只复制值，不带 `label:` 前缀。
- 空值不显示复制按钮/整行隐藏（与现有展示一致）。
- SnackBar 用 1 秒短提示，避免连续点多个字段时堆积；`ScaffoldMessenger` 的 `hideCurrentSnackBar` 可先调用再展示。
- 这是纯 Flutter 文本复制，不经过原生通道。

| 视频角标 | 网格视频 | 保留右上角播放角标 |
| 删除 | 详情页溢出菜单 → 删除 → 确认 | loading → 返回列表 → SnackBar → 列表少一项 |
| 删除同步 | 桌面端打开废纸篓 | 素材在废纸篓，可恢复；恢复后移动端 ws 刷新出现 |
| 二次删除 | 连点/重复 DELETE | 409 或幂等成功；`trashed_folders` 不被清空 |
| 详情内刷新 | 详情打开时桌面端改素材触发 ws | 不崩溃、不越界（列表快照生效） |
| 无库/未配对 | 桌面端关闭库/撤销 token | 删除/复制给出对应错误提示 |

## 10. 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 微信/ OEM 剪贴板 URI 权限差异 | 粘贴失败 | FileProvider 标准实现；保留分享兜底；验收矩阵记录机型 |
| 视频格式不支持 | 部分 avi/rmvb 无法播放 | 错误态提示 + 分享/下载；后续再评估 media_kit |
| video_player 增加 APK 体积 | 每架构 +2–4MB | 已按 ABI 分包；发布前记录体积 |
| GIF 大文件流量 | 网格卡顿/耗流量 | 8MB 阈值 + 静态回退；详情只加载当前页 |
| 删除误操作 | 素材进废纸篓 | 二次确认 + 废纸篓可恢复 + 文案说明 |
| 重复删除清空 `trashed_folders` | 恢复后目录丢失 | HTTP 409 + `MoveToTrash` 幂等保护 |
| 详情页与首页共享 List | 刷新时越界 | 详情页复制列表快照 |
| `photo_view` 动图不可靠 | GIF 静止 | GIF 不走 PhotoView，改用原生 `Image` |
| 剪贴板缓存占用 | 存储增长 | 500MB 上限 + 24h 清理 |
| 删除接口被滥用 | 误删 | 仅 Bearer 鉴权；语义为废纸篓；无永久删除 |

回滚点：

- 删除接口：仅新增方法分支与错误码，回滚 `core/mobile_api.go`/`errors.go` 即恢复；无数据库迁移。
- 剪贴板：回滚 `MainActivity.kt`、manifest provider、`file_paths.xml` 和 `api_service.dart` 的两个方法即可；不影响其他功能。
- 视频：移除 `video_player` 依赖和播放器页面，恢复 `PhotoViewGallery` 即可；不影响图片浏览。
- GIF：静态图路径不变；回滚只需恢复 PhotoView 使用。

## 11. 明确不做

- 不做移动端废纸篓列表/恢复（恢复仍在桌面端）。
- 不做永久删除。
- 不做视频全屏手势/画中画/后台播放。
- 不做自定义 ContentProvider 流式剪贴板。
- 不做服务端动图缩略图生成。
- 不做音频详情播放（本期只保证视频，音频仍显示占位/破图，保持现状）。
- 不改桌面端 Wails 绑定，不改 `frontend/bindings/**`。
