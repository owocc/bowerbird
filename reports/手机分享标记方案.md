# 手机分享条目本地标记方案

日期：2026-10-21
分支：`feature/mobile-share-intent`
范围：仅 `mobile/`（本地标记），不改桌面端 `core/` 与 `frontend/`。

## 1. 条目 ID 与文件 SHA-256 的对应关系

### 1.1 验证结论

结论：**条目 ID 就是原始文件字节的 SHA-256，大写十六进制（64 字符）**；对所有文件类型成立；桌面端上传链路不做转码，因此移动端对同一个上传文件计算 SHA-256 即可得到条目 ID。

代码证据（`core/library.go`）：

- `copyAndHashFile` 边拷贝边哈希，读到的就是源文件原始字节，结束后
  `contentHex = strings.ToUpper(hex.EncodeToString(sha256.Sum(nil)))`
  （`core/library.go:1309-1364`）。
- `prepareSingleFileImport` 直接 `itemID := contentHex`（`core/library.go:1438`），随后目录、数据库主键都用该值。
- Base64/字节导入同样 `ComputeBytesSHA256` → `itemID := contentHex`（`core/library.go:1629-1669`）。
- `ComputeFileSHA256` / `ComputeBytesSHA256` 均返回 `strings.ToUpper(...)`（`core/library.go:2371-2387`）。

上传链路无转码证据（`core/mobile_api.go:749-843`）：

- multipart 每个 part 用 `io.Copy` 原样落盘（`core/mobile_api.go:799-814`），再交给
  `ImportFilesWithProgress`，后者走上面的 `copyAndHashFile`。
- 桌面端只额外生成缩略图/元数据，不修改原文件字节，因此 ID 不受图片格式、GIF、视频、音频、文本等类型影响。
- 重复内容入库时返回已有条目（`core/library.go:1412-1435`），ID 仍是内容哈希。

移动端侧：

- 文件条目上传前位于收件箱，`ApiService.uploadFiles` 用
  `MultipartFile.fromPath` 读取同一文件，字节不变。
- 文本条目在上传时写成 UTF-8 `.txt`（`InboxService._writeTextFile`），桌面端哈希的就是这些 UTF-8 字节，同样可本地计算。
- 因此本地 `SHA-256(file bytes)` 与服务端 ID 一致，大小写统一转大写即可。

### 1.2 兜底匹配策略

桌面端上传接口响应本来就带回了本次导入的条目数组：
`{"status":"success","count":N,"items":[...]}`（`core/mobile_api.go:836-842`），
每个元素含 `id`。这是最权威的对应关系，不需要额外请求。

实现顺序：

1. 上传返回 200 后，优先取响应 `items[].id`（本次只传一个文件，取第一个）。
2. 响应缺少 `items`/无法解析时，退回本地计算的 SHA-256（转大写）。
3. 两者都拿不到则不写标记，宁可漏标也不误标。

不采用“刷新列表后按文件名 + 大小 + 时间窗匹配”的原因：上传响应已经提供精确 ID，
额外刷新有分页/竞态成本，且同名同大小文件可能误配。文件名匹配只在未来接口退化时才有价值，
本次记入待验，不实现。

### 1.3 已知限制

- 若桌面端在手机侧不知情的情况下修改了库名，本地标记的库键会对不上，表现为不再显示角标；
  数据仍保留，改回同名库即可恢复。标记是可丢的展示信息，不做服务端回填。

## 2. 本地存储设计

### 2.1 位置与结构

复用收件箱的持久化根目录与写入方式：

- 位置：`<应用文档目录>/share_inbox/share_tags.json`
- 写入：先写 `.tmp` 再 `rename`，失败时直接覆盖；与 `InboxService._writeIndex` 相同的原子写策略。
- 结构：

```json
{
  "version": 1,
  "marks": [
    { "id": "64位大写HEX", "library": "库名", "sharedAt": 1760000000000 }
  ]
}
```

- `id` 统一转大写，加载时只接受 `^[0-9A-F]{64}$` 的记录，丢弃损坏项。
- `library` 是标记产生时的活动库名（`ApiService.libraryName`，为空时用 `default`）。
  不把服务器 IP/端口放进 key：手机在家 Wi-Fi / Tailscale 间切换时地址会变，
  用地址会导致标记全部失效；库名在单机使用场景足够区分。
- `sharedAt` 为写入时刻（毫秒）。

### 2.2 查询与清理

- 网格/详情只显示“当前活动库键”下的标记；切换库后其他库的标记不出现，切回时恢复。
- 同一 `(library, id)` 重复写入只更新时间戳，不产生重复项。
- 容量上限 2000 条；超出时按 `sharedAt` 从旧到新删除，避免 JSON 无限增长。
- 移动端删除条目成功（详情页、长按预览删除）后调用 `forget(id)` 立即移除标记。
- 桌面端删除、或条目被移入废纸篓时手机无法感知：保留标记。内容寻址下同 ID 必然同内容，
  按任务书“可接受”；不为此轮询整库。
- 文件损坏/格式非法：忽略并当作空集合启动，下次写入时覆盖，不影响 App 其他功能。
- 不做历史回填：上传成功后收件箱条目与本地文件都会被删除，索引只保留事件 ID，没有文件路径，
  无法可靠重算旧条目的哈希。方案明确为“只从本次版本起标记”，不硬做。

## 3. UI 设计

### 3.1 网格角标

- 位置：缩略图**左下角**，小 chip，`Colors.black54` 圆角 4，白色 `Icons.ios_share` + 「分享」。
- 字号 9、图标 9–10，内边距与现有 GIF 角标一致。
- 不遮挡现有角标：GIF 在左上，视频/音频在右上，分享 chip 独占左下。
- 应用范围：主页月份网格、搜索页结果网格。
- 数据来源：`ShareTagService.isMarked(item.id)`，纯本地判断，不加网络请求。
- 主页订阅 `ShareTagService` 的通知，上传完成后自动刷新角标。

### 3.2 详情页

- 底部信息栏：在文件名/尺寸下方显示「手机分享」chip（同色系半透明白底），
  与现有标签 chip 并列但位于其前。
- 元数据抽屉：增加一行「来源：手机分享」，只有命中标记时出现。
- 不修改现有标签、文件夹、筛选逻辑。

### 3.3 与服务端标签体系的关系

- 本地标记**不进入** `/api/v1/tags`，不出现在标签 chip 列表、筛选面板或搜索过滤中。
- 仅作为来源提示；与服务端标签互不写入、互不覆盖。

## 4. 影响面

- 打标记：只在 `InboxService.uploadEntries` 成功分支（文件与文本都覆盖）；
  手动上传、分享后自动上传、全部上传都走该函数，逐项成功逐项标记，失败不写。
- 不打标记：主页 FAB 的普通上传（`home_screen.dart` 的 `uploadFiles`）保持原样。
- 删除：详情页与长按预览删除成功后清理标记。
- 初始化：`main.dart` 在 `InboxService.init()` 后初始化标记服务，失败不阻塞启动。
- 既有收件箱行为（幂等、逐项上传、角标计数）不变；标记为纯增量。

## 5. 验证计划

- 单测：SHA-256 已知向量、文件流式哈希、标记集合读写/库隔离/容量淘汰/损坏恢复。
- `flutter analyze` 无问题，`flutter test` 全过。
- 构建 `android-arm64` release APK，重命名为 `bowerbird-sharertag-1021.apk`。
- 真机清单：微信分享图片 → 网格出现「分享」；普通上传无角标；重启后标记仍在；
  删除条目后标记消失；切换库不串标。
