# 桌面查询引擎接入实施报告

> 分支：`feature/mobile-share-intent` ｜ 方案：`reports/桌面查询引擎接入方案.md`
> 范围：`frontend/` 数据层 + `core/` 桌面查询入口；未改 `mobile/`、未改 `/api/v1/query` 语法
> 结论：桌面活动库的浏览/搜索/筛选/排序已改由 core 查询引擎分页执行；5,000 条 seed 库首屏 IPC 从 **7.33 MB / 9.57 ms** 降到 **293 KB / 0.44 ms**，渲染进程数据堆从 **8.18 MB** 降到 **0.33 MB**。UI 冷启动和截图因沙箱无法启动 GUI 未能实测，已列待验。

### 1.1 前端内存过滤盘点与去向

| 现有条件 | 去向 |
|---|---|
| 搜索（name/tags/extension/hex/note/prompt 子串） | 改发查询；输入整体引号转义，语义仍是“字面子串” |
| type / color / orientation / size / has url / has note | 改发 `type:` / `color:` / `orientation:` / `size:` / `has:` / `no:` |
| 标签侧栏选中 / 仅看有标签 | 改发 `tag:` / `has:tag` |
| 未标记 / 未分类 | 改发 `is:untagged` / `is:uncategorized` |
| 文件夹视图（不含子文件夹） | 改发 `folder:<id>` |
| 文件夹视图（含子文件夹） | 语法无法 OR：桌面 RPC 增加 `folderScope[]`，与查询串 AND |
| 评分 1–5 | 改发 `rating:n` |
| 评分 = 未评分(0) | 语法只支持 1–5：桌面 RPC 增加 `onlyUnrated`，未改语法 |
| 文件夹下拉 / 排序 | 改发 `folder:` / `sort`（`importedAt desc/asc`，与旧路径一致） |
| 废纸篓 | 保留 `GetTrashItems` + 客户端过滤（未纳入本轮分页） |
| 拖拽历史 | 记录只有少量 itemId，改为并发 `GetItem` 逐条解析 |
| 侧栏总数/未标记/未分类/总大小/顶部颜色/子文件夹封面 | 改由 `GetWorkspaceStats`、`GetFolderPreviews` 供数，口径与原实现一致 |

活动库视图现在 `filteredItems = items`（服务端已过滤）；只有废纸篓、历史仍在前端过滤。

### 1.2 事件与分页共存

- `upserted / trashed / updated` 到达：沿用原有乐观局部更新（新条目插入、废纸篓项立即消失），随后 **150ms 合并防抖**，按当前查询并行重跑“已加载页数”的窗口，整体替换并校正 `total/totalSize`。
- 每次请求带自增版本号，过期响应直接丢弃；滚动加载也校验当前查询签名，避免旧查询页拼进新结果。
- 取舍：没有做“逐条判断是否命中当前查询”的局部增量。桌面组合过滤含 OR scope/未评分，逐条判断等于在渲染进程复制查询引擎；重跑 1–5 页的代价换语义正确。
- 事件到达时保持已加载深度与滚动位置，不回退到首屏。

## 2. 性能实测（改造前 vs 改造后）

环境：MacBook Air M1 / macOS 27.0.1 / Go 1.27.1 / Node 26.10.0；seed 库 `scripts/seed-perf-library.sh /tmp/bowerbird-perf-5000.library 5000`（5,000 条，20 文件夹，固定标签/颜色/尺寸分布，缩略图硬链）。

### 2.1 5,000 条 seed：数据层同口径

后端数字为对 5,000 条 seed 库 `index.db` 连续 10 次查询+`json.Marshal` 的中位数（同一路径已固化为 `BenchmarkWorkspaceDataPath`，synthetic cache 下首页约 0.32 ms / 118 KB，作为交叉验证）；渲染侧用 Node 26 对同一份 JSON 做 `JSON.parse` + `--expose-gc` 堆差，各 3 次取中位数。

| 指标 | 改造前 | 改造后 | 变化 |
|---|---:|---:|---:|
| 全量浏览首屏：后端查询+JSON | **9.57 ms** | **0.44 ms** | **21.8× 更快** |
| 首屏 IPC 字节数 | **7,327,505 B（7.33 MB）** | **293,203 B（293 KB）** | **25.0× 更小** |
| 渲染进程 `JSON.parse` | **14.49 ms** | **0.54 ms** | **26.8× 更快** |
| 解析后 JS 堆增量（数据常驻） | **8.18 MB** | **0.33 MB** | **24.8× 更小** |
| 典型 `tag:tag-7`（250 条命中） | 9.57 + 14.49 + 0.13（前端过滤）= **24.19 ms** | 0.47 + 0.56 = **1.03 ms** | **23.5× 更快** |
| 典型 `color:#EF4444`（1,250 条命中） | 9.57 + 14.49 + 1.14（前端过滤）= **25.20 ms** | 1.05 + 0.55 = **1.60 ms** | **15.8× 更快** |
| 侧栏统计聚合 | 原由全量数组在渲染进程计算 | **0.043 ms**（服务端） | — |

“库打开 → 首屏数据可用”（不含 webview 启动/绘制）：

| 阶段 | 改造前 | 改造后 |
|---|---:|---:|
| OpenLibrary | 8.7 ms | 8.7 ms |
| 内存索引加载 | 55.1 ms | 55.1 ms |
| 首屏数据查询+JSON 解析 | 9.57 + 14.49 = 24.06 ms | 0.44 + 0.54 = 0.98 ms |
| 合计 | **87.9 ms** | **64.8 ms（1.36×）** |

### 2.2 真实 37k 库（后端路径 + 既有 UI 日志基线）

改造前 UI 日志（现有 `app.log`，同一台机器，37,354 条）：`Loaded library items` **1,129 ms**、`Full item index rebuilt` **11 ms**、`Gallery TypedArray layout computed` **26 ms**（另一轮 37,354 条记录）。更早冷启动轮次出现过 3.4–8.7 s。

改造后对同一 `index.db` 副本实测（200 条/页）：索引加载 **463.9 ms**、首页查询 **1.03–1.22 ms**、首页 JSON **337 KB**、`color:#EF4444`（3,015 命中）**12.7–13.6 ms**。按“索引加载+首页查询+解析”计约 **466 ms**，相对上述 1,129 ms 的 UI 加载日志约 **2.4×**；这是后端数据路径对比，不等同于完整 UI 可交互时间。

### 2.3 未能实测的部分（必须说明）

沙箱下直接执行和 `open`（含 `--env` 隔离 profile）新构建均无法启动 GUI，进程在写 `app.log` 前退出，且没有审批通道可提升权限。因此：

- **冷启动到首屏可交互（完整 UI）**、**首屏渲染帧耗时**、**WebKit 渲染进程 RSS**、**截图自查**：本轮没有改造后真机数字。上面的内存/解析数字是“渲染进程数据层”口径，不是 WebKit RSS。
- 已用既有 37k UI 日志给出改造前真实基线，并明确标注改造后为后端路径数据。

## 5. 已知取舍 / 顺手项

- **废纸篓未分页**：`GetTrashItems` 仍是全量；活动库目标已达成，废纸篓大库仍可能全量传输。
- **`go tool mygo generate` 未跑通**：需在桌面 CGO 构建标签下生成；本轮手工同步客户端，后续应补一次正规生成。
- **顺手项未修**：盘点到的重复刷新点有三处，本轮优先保 1/2 未动：
  1. `library-items-updated` → `onRefresh()` → `handleFullRefresh()`，只改备注/评分也会重取 items+folders+tags+trash；
  2. `import-completed` 携带 inline items 时走局部 upsert，若同批又收到 `library-items-upserted` 会重复写状态；
  3. 删除失败 catch 分支在事件之外再 `handleFullRefresh()`。
  最热的是第 1 处，建议下一轮把 `library-items-updated` 改为只重跑当前查询窗口，不刷新 tags/trash。
